
## 🔄 ADR-003: Использование Apache Kafka для асинхронной обработки сканирований
**Статус**: Принято  
**Дата**: 2025-11-10  
**Участники**: Backend Architect, DevOps Engineer, Data Scientist

#### 1. Контекст и проблема
> "Как обрабатывать пиковые нагрузки до 1000 одновременных сканирований (SCAL-012), обеспечивая надежность и сохранение порядка запросов от одного пользователя (PERF-005)?"

#### 2. Архитектурно значимые требования (ASR)
| ID требования | Текст требования | Тип | Источник |
|---------------|------------------|-----|----------|
| SCAL-012 | Обработка $1000+$ одновременных запросов | НФТ | Техзадание п.4.1 |
| PERF-005 | Задержка в очереди $\leq 2$ сек | НФТ | Вывод из PERF-001 |
| REL-001 | Гарантированная доставка запросов на анализ | НФТ | Бизнес-требование BR-105 |

#### 3. Анализ альтернатив
| Требование \ Решение | RabbitMQ | **Apache Kafka** | Redis Pub/Sub |
|----------------------|-----------|-------------------|---------------|
| **SCAL-012 (Пиковая)** | ⚠️ | **✅ Оптимизирован под высокие нагрузки** | ✅ |
| **PERF-005 (Задержка)** | ✅ | **✅ Низкая задержка** | ✅ |
| **REL-001 (Надежность)** | ✅ | **✅ Гарантированная доставка, репликация** | ❌ |
| **Порядок сообщений** | ✅ (для очереди) | **✅ Гарантирован в рамках партиции** | ❌ |
| **Сложность** | Средняя | **⚠️ Высокая** | Низкая |

#### 4. Выбранное решение
**Apache Kafka** в составе кластера из 3 брокеров с конфигурацией:
- **Топик**: `scan-requests` с 6 партициями и фактором репликации 3.
- **Продюсеры**: Отправляют запросы с ключом `user_id` для гарантии порядка обработки запросов от одного пользователя.
- **Консьюмеры**: Группа `ai-analysis-group` для горизонтального масштабирования обработки.

#### 5. Обоснование
- **SCAL-012**: Kafka — это система потоковой обработки, созданная для высокой пропускной способности и горизонтального масштабирования.
- **REL-001**: Репликация (фактор 3) обеспечивает сохранность данных и отказоустойчивость при сбоях брокеров.
- **PERF-005**: Использование ключа `user_id` гарантирует порядок обработки для каждого пользователя, что критично для консистентности.

#### 6. Последствия
- ✅ **Позитивные**:
  - Отказоустойчивость и масштабируемость.
  - Гарантированный порядок обработки данных в рамках пользователя.
- ⚠️ **Негативные**:
  - **Операционная сложность**: Требует управления кластером и мониторинга (JMX, Prometheus).
  - **Дополнительные ресурсы**: Для работы кластера потребуется $\sim 4-6$ GB RAM.
- 🔧 **Зависимости**:
  - ADR-001: Консьюмеры Kafka передают текст в AI-модель для анализа.

#### 7. Верификация
| Метод проверки | Результат | Соответствие | Статус |
|----------------|-----------|--------------|--------|
| Нагрузочный тест (Locust) | 1200 RPS, задержка $<1.5$ сек | SCAL-012, PERF-005 | ✅ |
| Chaos-тест (остановка 1 брокера) | Обработка продолжается без потерь | REL-001 | ✅ |
